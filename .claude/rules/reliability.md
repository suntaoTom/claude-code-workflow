# 后端可靠性规范

## WebSocket

- 握手身份必须在进入业务处理前校验；用户类型、连接数、消息大小、频率、心跳和超时均配置化。
- Session 注册/摘除必须幂等；重复关闭不能重复扣减连接数或 Presence。
- 传输层只处理协议和显式路由，不解释订单、报价、资金等不透明 Payload。
- 本机内存中的临时回复路由必须明确单实例或粘性路由限制；多副本不能默认共享。

## RabbitMQ

- 消费必须定义 messageId、业务幂等键、correlationId 和 traceId 的不同语义。
- Inbox 必须有可查询状态和唯一约束；业务副作用不能因重复投递重复产生。
- Outbox 与业务事务边界必须可解释；Relay 只有 Confirm ACK 且无 Return 才标记发送成功。
- 重试必须有上限、退避和终态；禁止无限回流。达到上限进入 DLQ 或人工处置状态。
- 参数/契约错误和消息转换 fatal 不得自动重试；基础设施异常按明确策略治理。
- 新旧 exchange、queue、binding 的 durable、TTL、DLX 和 arguments 必须兼容；迁移完成前不得删除旧资源。

## 数据与缓存

- 数据库事务、唯一键、锁和缓存一致性由 Service/DAO 任务明确；不依赖“最终会一致”的模糊描述。
- Redis Presence、TTL 和锁必须有失效/重启行为；服务启动清理残留状态需可追踪。
- 定时任务、线程池、连接和租约必须可停止、可监控，避免重复执行。

## 可观测性

关键状态、重试、DLQ、超时、连接数、积压和业务失败需有结构化日志/指标/trace；不记录完整 Payload 或敏感字段。
