# 标准需求提报规范(/prd 的输入契约)

> **给谁看**:任何要提需求的人(产品 / 业务 / 运营 / 老板的一句话)。
> **为什么**:`/prd` 是「需求 → PRD → 任务 → 代码 → 测试」链的起点。**输入有多烂,后面就有多痛**——
> 残缺需求进来,AI 只能边写边一点点追问(chatbot 式补齐),漏掉的往往拖到开发/测试才暴露,返工最贵。
> 这份规范把「一个能直接开干的需求该长什么样」钉死。**不要求 100% 完美,但下面🔴的部分缺了就别提**。

---

## 一、一份「能直接进 /prd」的需求,必须回答这些

按重要性排(🔴 缺了基本没法做 / 🟡 缺了能用默认值但最好给 / 🟢 锦上添花):

| # | 要素 | 缺了会怎样 | 级别 |
|---|------|-----------|------|
| 1 | **做什么 + 给谁用 + 解决什么问题**(一句话) | 方向都不清,全盘跑偏 | 🔴 |
| 2 | **核心流程**:用户从哪进 → 做哪几步 → 到哪结束 | 不知道要搭什么页面/组件 | 🔴 |
| 3 | **业务规则**:每个功能点「当…时,应…」(见第二节,**最重要**) | 没规则 = 没测试断言 = bug 到测试才发现 | 🔴 |
| 4 | **异常/失败场景**:接口失败 / 无权限 / 数据为空 / 超时 / 校验不过,各怎么办 | 边界到开发才想起,反复补 | 🔴 |
| 5 | **字段/表单**:名称 / 类型 / 必填 / 校验规则 / 默认值 | 表单做出来对不上 | 🟡 |
| 6 | **范围边界**:本期**做什么** + 明确**不做什么** | 范围蔓延 / 做了又删 | 🟡 |
| 7 | **验收标准**:怎么算「做完了」(可验证,不是「做好」) | 没法判收,扯皮 | 🟡 |
| 8 | **数据来源**:接口有没有?路径/字段?没有的话先 mock(MSW)还是等后端? | 联调才发现接口不存在 | 🟡 |
| 9 | **设计稿**:UI 类需求给 Figma 链接/截图 | 没设计稿 → 视觉全凭猜,Visual QA 无基准 | 🟡 |
| 10 | **依赖/前置**:依赖现有哪个页面 / 登录态 / 权限 / 全局状态 | 串不起来 | 🟡 |
| 11 | **优先级 / 期望排期** | 排不上号 | 🟢 |

> 上游若来自**产品文档 / 设计稿 / OpenAPI**,引用要**真实可查**(给文件:行号或链接),别凭空写「与产品确认」。
> 详见 [`.claude/rules/upstream-fidelity.md`](../../.claude/rules/upstream-fidelity.md)。

## 二、重中之重:业务规则怎么写(测试断言全靠它)

**80% 的「开发/测试才发现需求不对」,根因是没把业务规则讲清。** 规则是后面 `/test` 生成测试的唯一来源。

### 写法:每条用「当 X 时,应 Y」,可测、不含技术实现

✅ 好规则:
- 邮箱格式不合法时,失焦后实时显示「邮箱格式错误」,并禁用「提交」按钮
- 所有筛选字段为空时,搜索按钮禁用
- 连续输错密码 5 次,锁定账号并提示「请 30 分钟后再试」
- 接口返回 code=40301 时,跳转 `/403`;返回 50001 时 retry 1 次后弹 toast

❌ 别这样:
- 「做个表单校验」(校验什么?不合法怎么表现?)— 太空
- 「用 debounce 处理输入」(这是实现,不是规则)— 越界
- 「按常理处理异常」(常理是什么?)— 等于没说

### 一条规则的自检:它能不能变成一句测试?
> 「当输入 `not-an-email` 并失焦时,应看到『邮箱格式错误』且提交按钮禁用」→ 能直接写成 `it()` ✅
> 「邮箱要校验」→ 写不出测试 ❌,退回去补。

## 三、好需求 vs 坏需求(同一个需求两种写法)

### ❌ 坏(典型的「一句话甩过来」)
> 「做个用户列表,能搜索。」

→ /prd 收到只能反问一二十个问题,且很多要到开发才暴露:搜什么字段?分页?空结果怎么显示?接口在哪?权限?……

### ✅ 好(同一需求,够开干)
> **做什么**:后台用户列表,支持按手机号/状态筛选。给运营查用户用。
> **流程**:进列表页 → 填筛选(手机号/状态)→ 点搜索 → loading → 列表更新 / 空态。
> **业务规则**:
> - 手机号格式不合法(非 11 位 1 开头)→ 实时红字,搜索按钮禁用
> - 所有筛选为空 → 搜索按钮禁用
> - 重置 → 清空字段并自动查一次(不用再点搜索)
> - 无权限(40301)→ 跳 `/403`
> **字段**:手机号(string,11 位校验,选填)、状态(enum:启用/禁用/全部,默认全部)
> **异常**:接口超时 → 显示「加载失败,重试」按钮;结果为空 → 显示空态组件
> **范围**:本期只读列表 + 筛选;导出 Excel 不做。
> **数据来源**:`GET /api/users/search`(已有,见 OpenAPI `searchUsers`);分页每页 20。
> **验收**:输合法手机号 → 列表按条件刷新;空结果显示空态;无权限跳 403。

(差距一目了然。坏需求的代价是后面反复口述补;好需求一次进 /prd 就能拆。)

## 四、「可以提交了」自检清单(勾完再提给 /prd)

- ☐ 一句话说清:做什么 / 给谁 / 解决什么
- ☐ 核心流程从头到尾走得通(每步谁触发、到哪结束)
- ☐ **每个功能点至少 2-3 条「当…应…」业务规则**,且每条能想象成一个 `it()`
- ☐ 列了主要失败场景(接口失败 / 无权限 / 空数据 / 超时 / 校验不过)
- ☐ 关键表单字段:必填 + 校验规则
- ☐ 明确写了「本期不做什么」
- ☐ UI 类需求附了 Figma/截图(或注明暂无)
- ☐ 接口:复用现有 / 待后端 / 先 mock(MSW),三选一标清
- ☐ 上游引用真实可查(产品文档:行号、设计稿:文件、接口:OpenAPI operationId)

> 勾不满没关系——**至少把🔴(1-4 项)写清**,🟡 缺的可以让 /prd 用默认值推进(会标 `[默认假设]`)。

## 五、给 AI 的:`/prd` 收到外部需求后的入口关口(强制)

> 目的:把「逐条 chatbot 式补齐」压缩成**一次批量澄清**,并把缺口暴露在最前面,而不是 dev/test。

`/prd` 拿到外部需求(文字 / docx / 截图)后,**第一件事**是对照本规范第一节做**缺口扫描**,一次性输出:

```
需求完备性扫描(对照 _intake-spec.md):
  🔴 阻塞(必须先补,否则 PRD 写不实):
     - 缺「业务规则」: 搜索失败/空结果时的表现没提
     - 缺「核心流程」: 用户从哪个入口进?
  🟡 可默认推进(我按主流方案填,会在 PRD 标 [默认假设],请回头确认):
     - 分页大小 → 默认每页 20
     - 失败重试 → 默认 retry 1 次
  🟢 可后补(不阻塞,记 TODO):
     - 优先级 / 排期
```

处理:
- **🔴 必须先补**——把这些**一次性**列给用户(用 AskUserQuestion 批量问),补齐再往下,不要边写边一条条追。
- **🟡 用默认值推进**,但 PRD 里必须标 `[默认假设]`,让用户回头一眼看到哪些是 AI 拍的。
- **🟢 记 TODO**,不打断。

这样用户体验从「被 AI 反复追问 + dev 才发现漏」变成「开头看一张缺口清单,补一次,后面顺畅」。

> 注:这是**入口分诊**,不替代后续 `/prd-check` 的硬门禁(`[待确认]` 清零等)。两者一前一后。
